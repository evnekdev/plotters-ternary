# Plotters integration spike

## Scope and result

This Milestone 0 experiment is deliberately confined to
`examples/plotters_spike.rs`; it introduces no ternary-domain public API.

The Cartesian-backed approach works for the required integration points. One
generic `render` function accepts a Plotters `DrawingArea`, builds an internal
Cartesian `ChartContext`, and produces matching PNG and SVG figures. The SVG
contains vector `polyline` and `circle` primitives plus ordinary SVG `text`
nodes for the caption, marker label, and legend labels.

## Dependency and feature selection

The manifest selects `plotters = "0.3.7"` with default features disabled:

```toml
plotters = { version = "0.3.7", default-features = false, features = [
    "bitmap_backend",
    "bitmap_encoder",
    "svg_backend",
    "ttf",
] }
```

The resolved version for this spike is Plotters 0.3.7.

- `bitmap_backend` supplies `BitMapBackend`.
- `bitmap_encoder` enables saving its output as PNG.
- `svg_backend` supplies `SVGBackend`.
- `ttf` supplies Plotters' normal native system-font path for raster text.

Captions, `ChartContext::draw_series`, `SeriesAnno`, legend configuration,
`PathElement`, `EmptyElement`, `Circle`, and `Text` are available without
the optional built-in `line_series` or `point_series` features, so those
features are intentionally not enabled.

## Demonstrated integration

The experimental example draws an aspect-correct equilateral triangle and
three families of internal triangle-parallel grid lines. It also proves the
following ordinary Plotters facilities work together:

- a `ChartBuilder::caption`;
- styled `PathElement` series;
- a returned `SeriesAnno` configured with `.label(...).legend(...)`;
- `configure_series_labels().draw()`;
- an `EmptyElement::at((x, y)) + Circle + Text` composable marker.

The checked SVG contains the caption `Plotters Cartesian integration spike`,
the labels `Triangle boundary` and `Ordinary Plotters series`, the
`Composable marker` text, 16 `polyline` elements, and a `circle`; it
contains no `image` element. PNG and SVG are generated by the same renderer,
not by image conversion.

## Ownership, lifetimes, and escape hatches

A future `TernaryChart` can safely own a private Cartesian `ChartContext`.
`ChartBuilder::on(&root)` borrows the root only while building; the resulting
context owns a cloned `DrawingArea`, whose backend is internally shared by
`Rc<RefCell<DB>>`. It therefore does not retain a borrow of the root drawing
area.

The `ChartContext<'a, DB, CT>` lifetime remains important: it is the lifetime
used by stored `SeriesAnno` legend closures. The drawing backend can have an
independent lifetime as part of `DB`; for example, the file-path references
held by `BitMapBackend<'path>` and `SVGBackend<'path>` must outlive the
chart. No leaked allocation, unsafe lifetime extension, or `'static` bound is
needed.

Milestone 3 should let its wrapper own the context and offer narrow
`cartesian_chart(&self)` and `cartesian_chart_mut(&mut self)` escape hatches.
The plotting-area escape hatch can be borrowed from that context with
`ChartContext::plotting_area()`; the wrapper should not store a duplicate
drawing-area reference.

## Series annotations and legends

A ternary `draw_series` adapter should finish projection and mathematical
clipping into owned ordinary Plotters elements, then delegate to the internal
`ChartContext::draw_series`. It should return Plotters' mutable
`SeriesAnno<'a, DB>` directly, rather than inventing an annotation wrapper.
This preserves the normal `.label(...).legend(...)` chain and
`configure_series_labels` behaviour demonstrated by the example.

Legend closures are stored by Plotters, so a future adapter must not let them
borrow a short-lived projected series or temporary geometry. Legend closures
that only capture owned styles are straightforward. Drawing directly through a
plotting area is useful for raw annotations but does not allocate a
`SeriesAnno`, so it cannot replace the wrapper's `draw_series` path for
legend-bearing series.

## Clipping finding

Plotters 0.3.7 has layout subareas such as `DrawingArea::shrink`, but it does
not expose a portable scoped vector clipping path for an invisible ternary
viewport. In the normal element path, the `DrawingArea` rectangle is passed
to `BackendCoordOnly::map`, which truncates each mapped coordinate to the
rectangle. Per-coordinate truncation is not geometric segment or polygon
clipping: it can create a false boundary segment when a complete source segment
lies outside the viewport.

Mathematical clipping is therefore still required before Plotters drawing:
clip triangle-defined segments and polylines, split visible subpaths, and clip
polygons against the rectangular viewport. Start markers with a centre-based
visibility policy; true marker-bounds and text-bounds clipping need geometry or
a deliberately backend-specific extension. A shrunken drawing area remains
useful for layout, not as the ternary clipping implementation.

## Text and fonts

Plotters' native `FontTransform` supports only `None`, `Rotate90`,
`Rotate180`, and `Rotate270`. The SVG backend preserves those quarter turns
as SVG `<text transform="rotate(...)">`, so they remain vector text. There is
no arbitrary-angle transform in the common Plotters text API; in particular,
the +/-60-degree ternary-axis orientations cannot remain portable vector text
through that API. The first public text API should expose only quarter turns or
report unsupported arbitrary angles explicitly.

The `ttf` feature introduces native system-font discovery and its
font-related dependencies. Bitmap output consequently depends on an available
system font matching the requested family. SVG output writes a font-family
reference rather than embedding the font, so its final appearance also depends
on fonts available to the SVG viewer. A future portable or cross-compiled
configuration can instead investigate Plotters' `ab_glyph` feature, but that
requires explicit font registration and is outside this spike.

## Awkward approaches and risks

- Constructing a mathematical equilateral triangle is not enough to make it
  visually equilateral: the Cartesian range must account for the allocated
  pixel aspect ratio after caption and margin layout. The example calculates
  its Y range from the actual caption measurement and drawing dimensions.
- `ChartContext` has substantial generic parameters, and public error types
  must account for `DrawingAreaErrorKind<DB::ErrorType>`. Keep those details
  private until the builder and error model are validated.
- Stored legend closures make the chart's annotation lifetime part of the
  eventual public API design.
- Backend-font availability, SVG font substitution, marker/text bounds
  clipping, and arbitrary-angle text remain cross-backend risks.

## Decision

ADR 0001 remains valid and is confirmed for the initial implementation:
a Cartesian-backed wrapper preserves the needed Plotters layout, styled
elements, annotations, legends, composable elements, PNG output, and SVG
vector output. ADR 0002's mathematical-clipping decision is also reinforced.

The next recommended work is Milestone 1: build the backend-independent
composition and projection kernel. Milestone 2 must implement the clipping
algorithms before Milestone 3 exposes a rendered ternary chart.
